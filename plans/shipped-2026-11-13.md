# What shipped — 2026-11-13

The record of the `eggpass` implementation: what was built, where the build
diverged from the plan, what was verified against the real services, and the
two things that still need a human.

The plans that describe the design are
[`plan-eggpass.md`](plan-eggpass.md), [`implementation-plan.md`](implementation-plan.md)
and [`cli-spec.md`](cli-spec.md). This document is the outcome.

---

## The headline

`eggpass` is a single binary that authenticates against two providers with
their own subscription OAuth credentials and serves both behind one OpenAI-
compatible base URL:

| Provider | Auth | Upstream | Wire format |
| --- | --- | --- | --- |
| x.ai | OAuth 2.0 + PKCE, browser or device code | `https://api.x.ai` | Chat Completions, forwarded natively |
| ChatGPT | Sign in with ChatGPT for Open Source (SIWC) | `https://api.openai.com/v1` | Responses API, translated to/from Chat Completions |

Verified live against x.ai on 2026-11-13: the daemon starts, serves a live
13-model catalogue, answers a non-streaming chat completion, and streams a
second one incrementally.

## Build state

```
cargo test                                  139 passed, 0 failed
cargo clippy --all-targets -- -D warnings   0 warnings
cargo fmt --all -- --check                  clean
cargo build --release                       ok (4.0 MB)
```

Rust stable, MSRV 1.89, edition 2024, **no async runtime** — blocking,
thread-per-connection throughout.

### The dependency set, as built

Runtime: `serde`, `serde_json`, `toml`, `ureq`, `sha2`, `base64`, `rand`,
`daemonize`, `signal-hook`, `nix`, `dirs`, `webbrowser`,
`eggup-acquisition`, `eggup-core`, `eggup-eggpack`, `eggup-eggfetch`.

Development: `tempfile`.

The four `eggup` crates are the family's own update machinery — acquisition,
core, manifest projection and transport. `eggup-curl` was evaluated and
rejected: `CurlConfig` has no User-Agent seam and the adapter clears the child
environment, so every request goes out as `curl/x.y` and the release host
answers 403. A transport that cannot reach the version authority is not
qualified, however small it is.

## What was built, phase by phase

### Phase 0 — Server hardening (H1–H5)

The fixes from Part 1 of the plan:

- **H1** — the active-connection counter is now decremented *after* the
  response body is written, not when the handler returns. `SIGTERM` during a
  streaming response used to truncate it.
- **H2** — the upstream timeouts are configurable through a new `[timeouts]`
  config table. The body timeout was raised from 300 s to 1800 s: a long answer
  can take minutes to stream, and cutting one off mid-sentence is worse than
  waiting.
- **H3** — the local server's limits are configurable through a new
  `[server]` config table (`max_connections` 256, `idle_timeout_seconds` 120,
  `write_timeout_seconds` 600), and they are *real* limits, not hardcoded
  constants. Past `max_connections` the server answers `503`.
- **H4** — a drain wait on shutdown, so in-flight requests finish.
- **H5** — `x-xai-token-auth`, `x-grok-client-version` and
  `x-grok-client-identifier` are stripped from incoming requests. A client
  cannot inject the headers the provider owns.

### Phase 1 — `port` and `host`

Both commands validate, compare against what is **actually being served**,
probe the address, then stop → write → start, with a rollback.

The shared machinery lives in `src/cli/commands/address.rs`. The comparison is
against the **pid file**, not the config file, because those two can disagree —
the config says what the next start will use, the pid file says what is running
now. "Only restart if the value actually changed" is decided against the pid
file.

The order matters and is deliberate: **the port is checked for being taken
before anything is stopped.** A refused change leaves the daemon running, the
config untouched and the exit code `1`.

The pid file grew a third line — the bound host — so `host` can tell what is
being served. It is optional when reading, so a pid file written by an older
build still parses.

`host` defaults to loopback. `local`, `localhost` and `loopback` all mean
`127.0.0.1`. A non-loopback host is refused unless `api_key` is set, and warns
when it is allowed.

### Phase 2 — The static catalogue is gone

`KNOWN_MODELS` is deleted. `GET /v1/models` is a live round trip: the union of
the signed-in providers' catalogues, merged. A model id no provider advertises
is a `404`.

### Phase 3 — The provider layer

`src/provider/{mod,xai,openai}.rs` introduces `ProviderId`, `ProviderSpec`,
`RequestPolicy`, `CatalogueKind` and `NativePaths`. Credentials moved from one
`auth.json` to one file per provider:

```
~/.config/eggpass/credentials/xai.json      0600
~/.config/eggpass/credentials/openai.json   0600
```

Each provider has its own refresh mutex, so refreshing x.ai never blocks
ChatGPT.

Routing is a model-prefix map, longest prefix wins, with a default provider
for anything unmatched.

### Phase 4 — ChatGPT SIWC

`src/provider/openai.rs` carries the SIWC constants; `src/auth/client.rs` was
generalised to `OAuthClient::for_provider`, `authorize_url_with`,
`exchange_code_as`, `refresh_as` and `revoke`; `src/auth/flow.rs` was
rewritten to distinguish a **first registration** (client id
`dynamic_agent_client`, OpenAI issues the real one during the callback) from a
**reauthorization** (the issued id is reused, with `id_token_hint`). The
issued client id and the `ext_agent_host_id` are persisted.

The callback path is exactly `/auth/callback`, on a random ephemeral loopback
port, with `resource=https://api.openai.com/v1`. The exact 16 rejected fields
are stripped from every request.

### Phase 5 — ChatGPT inference

`src/server/aggregator.rs` aggregates the Responses API's SSE stream into a
single answer, with three outcomes: `Completed`, `Failed`, `Incomplete`. The
upstream slot is held for the **life of the stream**, not just for the handler
call — releasing it early was the source of the streaming-concurrency findings
in Part 1 of the plan.

`src/server/models.rs` merges the catalogues of the providers that are signed
in.

### Phase 6 — Chat Completions translation

`src/server/translate.rs` translates Chat Completions to the Responses API and
back. x.ai is still forwarded natively; only ChatGPT goes through the
translator.

### Phase 7 — Upstream headers

Upstream response headers now reach streaming clients (`sse::stream(headers, …)`).

`GET /v1/usage` was **not** implemented. The plan marked it optional and the
upstream contract could not be verified, and shipping a guessed contract would
be worse than shipping nothing.

### The interactive provider picker

`src/cli/prompt.rs`, on **`nix`'s termios** — the family's own terminal
selector, the one eggpool's `connect` command uses.

`j`/`k` and the arrow keys both move the cursor, and the cursor **stops at the
ends** rather than wrapping. `Enter` selects, `q` and `Esc` cancel, and
`Ctrl-C` interrupts — deliberately distinct from cancelling, so an
interruption exits non-zero while a cancellation exits `0` and changes
nothing.

The screen is **cleared and the menu redrawn from the top** on every
keystroke. The terminal is restored on **every** exit path, including a panic:
the raw-mode guard lives in a `Drop` implementation.

The interactive picker needs **both** stdin and stdout to be terminals. A
terminal on stdin with a pipe on stdout would put cursor-control sequences
into the pipe, so that combination uses the fallback instead.

When stdin is not a TTY the picker falls back to a numbered list and reads one
line — that fallback is not optional, because the command has to behave the
same in a pipe, in CI and in cron. `--provider <id>` bypasses the picker
entirely.

The picker is covered by **pseudoterminal tests**: the selector is driven
over a real PTY, so the key handling, the escape-sequence parsing, the
terminal restoration and the rendered frames are all verified against a real
terminal rather than a mock.

### The updater

`src/update.rs` is **policy only**; the mechanics are `eggup`'s.

- `host_target()` produces the exact Rust target triple. Aliases like
  `linux-x64` are not accepted.
- `classify_provenance()` detects a Cargo-managed install (by `.crates.toml`)
  and **refuses**, printing the `cargo install` command to run instead —
  replacing a Cargo-managed binary behind Cargo's back desynchronises the two.
  A self-managed install proceeds; an unprovable one is refused rather than
  guessed.
- Ownership is proven by `LiveDigestVerifier`: the destination must hash to the
  digest observed before the transaction began, re-read under `eggup`'s lock.
- The candidate is validated by `ExactIdentityValidator` — stdout compared
  exactly against `eggpass <version>\n`, run with `--version`.
- The commit uses `AbsentPolicy::DenyCreate`, so the transaction cannot create
  a file that should already exist.
- A receipt disposition of `RolledBack` or `RecoveryRequired` is handled: in
  the recovery case the previous binary's path is printed.
- **The daemon is never restarted.** A restart cuts live streams, and the user
  asked for an update, not an outage.

`eggup-eggpack` 0.2.0 pins `eggpack-manifest = 0.1.0`, so
`project_json(&[u8], target)` is used: the manifest is taken as bytes, which
avoids a type-identity conflict and means no version pin has to be mirrored in
`Cargo.toml`.

### The rename and the migration

The crate, the binary, `EGGPASS_HOME`, `eggpass.pid` and `eggpass.log` all
carry the new name. `src/migrate.rs` copies the old `~/.config/grokproxy`
directory's contents into `~/.config/eggpass` on startup, leaving a
`migrated-to-eggpass` marker behind in the old directory.

The migration **copies rather than moves** and never deletes anything the user
owns. It never overwrites an existing `~/.config/eggpass`, and it is
idempotent.

The migration runs after `Paths::resolve` and **before** `Config::load` and
`paths.ensure_dir()`, so the first run against a legacy install picks up the
old config and credentials rather than writing fresh ones over them.

The default `config.toml` is now written on first run
(`config::ensure_config_file`); it was defined but never called.

## Deviations from the plan

| Plan | What shipped | Why |
| --- | --- | --- |
| MSRV 1.85 | **MSRV 1.89** | `eggup`'s crate family requires it. |
| A bespoke updater | `eggup`'s published crates | There is no `eggup` crate — the family is `eggup-core`, `eggup-acquisition`, `eggup-eggfetch`, `eggup-curl`, `eggup-archive`, `eggup-eggpack`. Reimplementing their mechanics would have been a second, worse implementation. |
| eggpool's `update` as the updater reference | **cargo-cleanme** | eggpool's `update` is a Python-to-Rust migration artefact and non-standard for the family. cargo-cleanme is the standard-shaped consumer. |
| `eggup` as a facade crate | The real crate family | A facade would hide the seams the updater actually needs — a User-Agent, a manifest projection, a transaction with a lock and a rollback. |
| `ExistingAsOwnedVerifier` for ownership proof | `LiveDigestVerifier` | The former asserts ownership from configuration; the latter proves it by hashing the destination and requiring it to match the digest observed before the transaction, re-read under `eggup`'s lock. `ExistingAsOwnedVerifier` is documented as test-only. |
| `GET /v1/usage` | **Not implemented** | Optional in the plan, and the upstream contract could not be verified. A guessed contract is worse than none. |
| `port` never restarts (the old rule) | `port` and `host` apply **and** restart | Superseded by the design in Part 3.8.1 of `plan-eggpass.md`. |
| One `auth.json` | One file per provider | Part 3.2 of the plan. A provider's credential can be revoked and replaced without touching the other's. |
| The picker on **crossterm** | The picker on **`nix`'s termios** | The crossterm version rendered the menu as a staircase, because raw mode turns off the kernel's newline translation and a bare `\n` does not return to the first column. The rewrite follows the family's own terminal selector and comes with pseudoterminal tests. See [the picker was rendered wrongly](#the-picker-was-rendered-wrongly). |

## The one bug worth writing down

The provider base URL included `/v1` while the request path also carried the
`/v1` prefix. Every request went to `/v1/v1/...` and 404'd.

The fix: `Upstream::origin()` and `openai::api_origin()` return the **origin**,
never the origin plus `/v1`. The request path carries the prefix itself. Both
have regression tests that assert `base_url + path == "https://api.x.ai/v1/models"`.

The reason it was not caught by the unit tests is that the stub upstream
answered any path it was given. It was caught by the first live request.

### The picker was rendered wrongly

The first version of the picker was built on **crossterm**. It drew the menu
with `writeln!`, which emits a bare `\n`.

crossterm's `enable_raw_mode` calls `cfmakeraw`, and `cfmakeraw` clears
`OPOST` — the output post-processing that translates a line feed into
carriage-return-plus-line-feed. In raw mode a bare `\n` therefore steps down
one line **without returning the cursor to the first column**. The menu
rendered as a staircase, drifting right as it went down, and the redraw's
"move back up" logic compounded it.

The unit tests did not catch it: they asserted on the frame's contents, and
the frame did contain a newline — just not the two-byte sequence a raw
terminal needs. Only a real terminal shows the difference.

The picker was rewritten on **`nix`'s termios**, following the family's own
terminal selector (the one eggpool's `connect` command uses), and the
rendering now ends every line with an explicit `\r\n`. Two things came with
it that the old one got wrong:

- the screen is **cleared and the menu redrawn from the top** on every
  keystroke, rather than scrolled and patched;
- the interactive path needs **both** stdin and stdout to be terminals, so a
  terminal on stdin with a pipe on stdout no longer writes cursor-control
  sequences into the pipe.

The rewrite also added the behaviours the reference has and the old picker
lacked: the cursor **stops at the ends** instead of wrapping, `q` cancels as
well as `Esc`, `Ctrl-C` is an **interruption** rather than a cancellation, and
control bytes in a label are neutralised.

The picker now has **pseudoterminal tests** that drive the selector over a
real PTY, so this class of bug cannot come back unnoticed.

The cost: `crossterm` is no longer a dependency. `nix`'s `term` feature was
already going to be present for the tests, and `nix` was already a
dependency, so the dependency list got *smaller*, not bigger.

### xAI knows us as "Grok Build"

The xAI consent page introduces itself as Grok Build: *"Copy the code below
into Grok Build to finish signing in"*, *"Authorize Grok Build"*, *"We
couldn't check your Grok Build seat"*.

That is because we sign in with **the official Grok Build CLI's public client
id** (`b1a00492-…`) — the same public credential every Grok Build install
carries. xAI publishes no general-purpose public client for third-party
applications the way OpenAI now does with *Sign in with ChatGPT for Open
Source*, so there is no other id to use. xAI renders the page's `{clientName}`
from its client registry, and the registry maps that id to Grok Build. No
client-side setting changes it.

The `referrer` parameter is a **separate** thing, and it is where we are
honest. xAI's own CLI documents it as *"Referrer for OAuth usage attribution"*,
with a default of `user`; we send `eggpass`. Verified live: the authorize
endpoint accepts it and carries `referrer=eggpass` into the consent flow. It
does not change the page's wording, because the wording comes from the client
id.

### The login now accepts a pasted code

That page shows a **code to copy** rather than always redirecting to the
loopback, and the first implementation only listened on the loopback — so a
user who landed on the copy page was left staring at a code the tool could
not see, until the 10-minute timeout.

The official Grok CLI waits for the auth code from **"loopback + stdin"**
(`event crates/codegen/xai-grok-login/src/oidc/login.rs`). This now does the
same: while the loopback listener is open, a code pasted into the terminal is
picked up and exchanged. A pasted line that does not look like an
authorization code is ignored and the wait continues, and only a **terminal**
stdin is watched — reading a pipe would swallow the caller's input and would
block a scripted login forever.

The paste path is available for x.ai, whose client id is fixed. It is **not**
available for ChatGPT, which issues a client id of its own and returns it in
the callback: a pasted code carries no issued id to exchange. That
distinction is a field on the provider spec, `issues_client_id`.

Verified against the real xAI token endpoint: a pasted code is taken, sent
with the right client id and PKCE verifier, and rejected by xAI as
`invalid_grant` — which is exactly right for a code that was made up.

### The xAI login now matches OpenCode and the official CLI

Checked against
[`anomalyco/opencode`'s xAI provider](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/plugin/provider/xai.ts),
which uses the **same client id** and the same honest `referrer` approach —
`referrer: "opencode"` where we send `referrer: "eggpass"`. On that point the
two agree.

They differ on the **flow**. OpenCode registers exactly two methods for xAI:

- the device-code grant, and
- a manually entered API key.

There is **no browser method**. OpenCode used to have one, and its startup
path explicitly **migrates** every credential whose method is `browser` over
to `device`:

```ts
if (credential.value.type !== "oauth" || credential.value.methodID !== browserMethodID) return Effect.void
return credentials.update(credential.id, {
  value: Credential.OAuth.make({ ...credential.value, methodID: deviceMethodID }),
})
```

The official Grok CLI does the same thing at runtime — *"auth: device flow
unavailable (404), falling back to loopback login"* — so the device flow is
preferred and the browser is the fallback, not the other way round.

That is now how `eggpass login` works:

- the **device-code flow is the default** wherever the provider has one;
- if the device endpoint answers **404**, the browser flow is used
  automatically, with a note saying so;
- `--device` asks for the device flow explicitly and `--oauth` for the browser
  flow; giving both is a usage error.

The device flow is the better default on its own merits: it works from any
device, needs no browser on the machine and no loopback port, and — the
reason it matters here — it never shows the confusing *"Copy the code below
into Grok Build"* page, because the user **enters** a code rather than
copying one out.

Two smaller gaps against OpenCode were closed at the same time:

- the device poll now treats `authorization_denied` as a refusal, the way
  OpenCode does. xAI has used both `access_denied` and `authorization_denied`
  for the same thing.
- a `404` from the device endpoint is now `FlowError::DeviceUnavailable`,
  which is what drives the automatic fallback.

**Verified live against x.ai**: a real device-code login completed end to end —
code `S8VG-7BRV`, verification URL `https://accounts.x.ai/oauth2/device`,
approved, and a full credential written to `credentials/xai.json` (mode
`0600`) with an access token, a **refresh token**, an id token, the scope, the
client id, the expiry, the user id and the email.

That is a change in kind: until now the x.ai credential on this machine had
been **imported** from the official Grok CLI's `~/.grok/auth.json`. It is now
a credential `eggpass` obtained itself, through a flow `eggpass` drives.

## What still needs a human

Two things, and both are blocked on something outside the code.

> **The xAI login is no longer on this list.** It used to be: the credential on
> this machine had been *imported* from the official Grok CLI's
> `~/.grok/auth.json`, because the browser flow landed on xAI's confusing
> *"Copy the code below into Grok Build"* page. The device-code flow fixed
> that, and a real device-code login has since completed end to end, writing
> a full credential — access token, refresh token, id token, scope, expiry,
> user id and email — to `credentials/xai.json` with mode `0600`.

### 1. A completed ChatGPT sign-in

The SIWC implementation is complete and compiles, and the contract was
verified against OpenAI's documentation. It has **not** been exercised end to
end, because that needs a human to sign in with their ChatGPT account in a
browser and consent to plan usage.

What to run:

```sh
cd /Users/davidbowman/projects/grokproxy
cargo build --release
./target/release/eggpass login --provider openai
```

The browser opens the authorize URL on a random ephemeral loopback port with
the path `/auth/callback`. Sign in, consent, and the credential lands in
`~/.config/eggpass/credentials/openai.json` (mode `0600`).

Then check:

```sh
./target/release/eggpass status
curl -s http://127.0.0.1:8484/v1/models | python3 -m json.tool
curl -s http://127.0.0.1:8484/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"gpt-5","messages":[{"role":"user","content":"hi"}]}'
```

The ChatGPT models are advertised by `slug`, filtered to `visibility == "list"`.

### 2. A published release

`eggpass update` is implemented and its policy is tested, but there is no
published `eggpass` release for it to install. The repository
(`eggstack/eggpass`) is a **configured default**, not a confirmed fact — this
repo has no git remote.

To exercise it, publish a release with:

- an asset named `{product}-{canonical-triple}`, e.g.
  `eggpass-aarch64-apple-darwin` — version-free, so "latest" needs no
  rewriting;
- a manifest `eggpass-release-manifest.json` naming each artifact with its
  exact size, SHA-256 digest, member id and destination;
- the manifest reachable at
  `releases/latest/download/eggpass-release-manifest.json` for "latest" and
  `releases/download/v{version}/eggpass-release-manifest.json` for an exact
  version.

`eggpack` never publishes and claims no authenticity. The SHA-256 check is an
**integrity** check, not an authenticity check: it proves the download was not
corrupted, not that it came from us.

## What was deliberately not done

- **No database, no cloud, no admin API.** One binary, one config file,
  credentials never leave the machine, secrets never logged.
- **No launchd or systemd.** The daemon is self-contained and PID-file based.
- **No async runtime.** `eggserve` was evaluated and rejected: it requires
  tokio.
- **No eggpool features.** eggpass stays separate; eggpool ingests the OAuth
  layer downstream.
- **No deletion of user data.** The rename copies and leaves a marker. The old
  directory is the user's to remove.
- **No static model list.** The catalogue is live, so it cannot go stale.
