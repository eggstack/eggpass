# Cost of an async Eggpass auth library

## Recommendation

For downstream Rust repositories that already run async code and use Eggfetch, the useful migration target is a **public async authentication library**, not an async rewrite of Eggpass’s proxy server. The auth module is currently private to the `eggpass` binary (`src/main.rs:8-21`), so changing ureq calls to Eggfetch alone would not make the code consumable downstream. A focused `eggpass-auth` library—async OAuth/token methods and, if required, login flows—addresses the stated goal while leaving the custom blocking server and its SSE path intact.

My rough estimate for that full reusable auth surface, including keeping Eggpass’s current CLI and server operational, is **8–15 engineer-days (about 2–3 working weeks for one experienced Rust engineer)**. A narrower async OAuth client plus a small public API and consumer example, without porting the token manager or interactive login flows, is approximately **3–5 engineer-days**. A full Eggpass server conversion is a separate, substantially larger project; I would not undertake it for this downstream-reuse goal. These are code-review estimates, not measured implementation times; they assume provider behavior stays unchanged and carry roughly ±50% uncertainty until downstream API requirements are known.

## Where the work is

`OAuthClient` owns a ureq agent and synchronous exchange, device-code, refresh, revocation, and user-info calls (`src/auth/client.rs:167-220, 298-545`). Replacing those calls with Eggfetch is mechanically bounded: Eggfetch’s `Client` has async request methods, and request builders send with `.await`; response bodies can be collected or streamed asynchronously. The work is principally translating request construction, status/body/error mapping, user-agent and timeout policy, and the existing local-server tests—not reimplementing OAuth.

The larger change is state and flow behavior. `TokenManager::access_token` and `force_refresh` are synchronous, use `std::sync::Mutex`, and deliberately re-check credentials after taking the lock to collapse concurrent refreshes (`src/auth/refresh.rs:67-187`). Its async version must preserve that single-refresh property across `await`, preserve refresh-token rotation, and save credentials atomically. The current store uses synchronous filesystem operations and restrictive permissions (`src/auth/store.rs:1-18, 130-195`); it can remain a small synchronous boundary initially, but should not be accidentally weakened during extraction.

Login flows add another layer: device login polls with `std::thread::sleep`, while browser login uses a blocking loopback `TcpListener` and an optional stdin thread (`src/auth/flow.rs:127-289, 370-517`). A complete async login API needs to make polling cancellable and awaitable, and decide how to host the callback listener and terminal input. Separately, auth types depend on Eggpass’s combined provider description and credential paths, while the synchronous `TokenProvider` trait is declared in `src/upstream.rs:54-70` and consumed by request handling (`src/upstream.rs:207-229`). A downstream package should have a smaller OAuth-only provider configuration and storage boundary rather than importing server/config internals.

Eggpass’s server is intentionally blocking: it uses a standard `TcpListener`, spawns one OS thread per connection, and writes and flushes SSE chunks synchronously (`src/server/http.rs:166-253, 748-772`). That creates an integration boundary, but not a reason to make the HTTP server async. Eggpass can keep a small host-owned compatibility adapter for the current CLI/server while downstream crates call the auth library’s async API directly. Keep runtime bridging at that host boundary; do not hide runtime construction inside a reusable library. Tokio’s own guidance discusses explicit sync/async bridging and using blocking work at appropriate boundaries ([Tokio bridging](https://tokio.rs/tokio/topics/bridging), [Tokio `spawn_blocking`](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)).

## Effort by scope

| Scope | Estimate | Included work |
|---|---:|---|
| Async OAuth transport only | 3–5 engineer-days | Convert `OAuthClient` endpoint calls to Eggfetch; preserve timeouts, user-agent, status/error semantics; update HTTP tests; add a minimal consumer example. This does not make the current private module reusable unless a public library surface is added. |
| Recommended reusable auth package | 8–15 engineer-days | Add a public crate/API; isolate OAuth provider configuration from inference/config types; async OAuth and token refresh; preserve refresh serialization and credential-store guarantees; port device and loopback login as required; add a synchronous host adapter for Eggpass; test a downstream-style Eggfetch consumer. |
| Entire Eggpass application async | Several additional weeks; separate estimate | Replace or adapt the custom server, upstream request path, connection management, and synchronous streaming writer. This is outside the stated purpose and would increase risk without improving downstream auth ergonomics proportionally. |

The full package estimate assumes both browser and device login should remain supported. If downstream callers only need to exchange/refresh tokens after handling user interaction themselves, omitting the login-flow port should reduce the estimate by several days. Publishing a new crate also adds ongoing compatibility, documentation, and semver obligations beyond the initial implementation.

## Eggfetch version and integration cost

Eggfetch’s current published `eggfetch-core` is 0.3.0 (released 31 October 2026); its documentation describes it as async-first and demonstrates `.send().await` and async body reads ([0.3.0 docs](https://docs.rs/eggfetch-core/0.3.0/eggfetch_core/), [Client API](https://docs.rs/eggfetch-core/0.3.0/eggfetch_core/client/struct.Client.html)). Eggpass’s lockfile currently resolves `eggfetch-core` 0.2.2 through `eggup-eggfetch` 0.2.0, as confirmed by `cargo tree --locked --offline`. The published updater adapter remains at 0.2.0 and depends on `eggfetch-core ^0.2.0` ([adapter docs](https://docs.rs/eggup-eggfetch/0.2.0/eggup_eggfetch/); [crates.io version metadata](https://crates.io/api/v1/crates/eggup-eggfetch)). Therefore, adding a direct 0.3.x dependency for the new auth library will currently leave both 0.2.x and 0.3.x in Eggpass’s dependency graph. That is manageable, but has compile/binary-size and maintenance cost; it can be avoided later if the updater adapter is released against 0.3.x. Downstream consumers on 0.3.x should use the same major/minor line if the library accepts an Eggfetch `Client` from the caller.

Eggfetch’s `Timeout` supports separate pool, connect, write, read, and total deadlines ([timeout API](https://docs.rs/eggfetch-core/0.3.0/eggfetch_core/timeout/struct.Timeout.html)). The port still needs to deliberately map Eggpass’s existing OAuth agent policy (60-second global and 180-second body receive timeouts in `src/auth/client.rs:189-194`); phase-aware defaults should not silently change login behavior. ureq is explicitly a blocking-I/O client ([ureq 3.5.2 docs](https://docs.rs/ureq/3.5.2/ureq/)).

## Suggested implementation boundary

Create a small library crate with an OAuth-specific provider config, `OAuthClient` constructed with or accepting a clone of `eggfetch_core::Client`, and async token/refresh methods. Keep provider policy and token parsing in the crate; make credential persistence configurable or portable. Port the device and browser flow only if downstream callers need Eggpass to own those interactions. In the binary, adapt its current synchronous token-provider contract at the boundary, so the proxy’s ureq inference path and SSE implementation need not move in the same change.

Do not count this as a complete removal of ureq: it remains used by upstream inference, daemon health probes, and usage queries (`src/upstream.rs:91-204`, `src/daemon.rs:210-223`, `src/cli/commands/usage.rs:291-309`). Removing ureq from the dependency graph would require a broader, separately justified migration.
