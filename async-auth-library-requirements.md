# Requirements for a public async Eggpass auth library

## Recommendation and boundary

The deliverable should be a separate, small Rust library crate—provisionally `eggpass-auth`—rather than making the whole Eggpass application async. Eggpass currently has only a binary target: `src/main.rs` declares `mod auth`, and the OAuth types are not exported to downstream crates (`src/main.rs:8-21`). Its server deliberately uses blocking sockets, one thread per connection, and synchronous SSE writes (`src/server/http.rs:166-253, 748-772`). None of that needs to change for async downstream consumers to call reusable auth functions.

The library should expose an async OAuth core that accepts or can be built around an `eggfetch_core::Client`, but should not create a Tokio runtime, print to the terminal, open a browser, or assume that credentials live in Eggpass’s home-directory files. Keep CLI conveniences and the current synchronous `TokenProvider` integration in Eggpass as host-side adapters. That preserves the existing proxy architecture while letting async consumers call the library inside their own runtime.

At the time of this research, crates.io’s API returned “crate does not exist” for `eggpass-auth`; the name appears available but must be checked again before publishing. Eggfetch 0.3.0 is the current documented async API. Eggpass’s updater currently brings in Eggfetch 0.2.2 through `eggup-eggfetch` 0.2.0, which depends on the 0.2 line. A new direct 0.3 dependency will therefore coexist with 0.2.x until the updater adapter moves forward or the duplicate is accepted.

## Public API requirements

**Provider configuration must be auth-specific.** Do not export Eggpass’s full `ProviderSpec`: it mixes OAuth endpoints and scopes with inference URLs, request policies, headers, and catalogue formats (`src/provider/mod.rs:65-160`). Define a focused `OAuthProviderConfig` containing issuer/endpoints, client ID policy, scopes, callback path, and the provider-specific parameters the OAuth requests need. Include the current x.ai and OpenAI profiles, while allowing callers to construct a compatible profile without importing Eggpass server/config modules. Preserve OpenAI’s issued-client-ID behavior and registration-only parameters, and x.ai’s client ID, `referrer` fallback, and device-flow support (`src/provider/xai.rs:75-100`; `src/provider/openai.rs:149-198`).

**Separate protocol from user interaction.** The core should offer async operations for authorization-code exchange, refresh, revocation, user-info, device-code creation, and polling. For browser authorization, provide a session/transaction API that returns the authorization URL and later accepts a validated callback; keep the verifier, state, and nonce inside an opaque pending-session value. An optional loopback helper can bind a random loopback port, but terminal prompts, browser launching, and stdin handling belong in an optional adapter or in the downstream application. For device authorization, return the verification URI and user code as data; let the caller decide how to present them, then poll asynchronously with cancellation support.

**Make credentials caller-owned by default.** Provide token parsing and refresh operations independently of the current `~/.config/eggpass/auth.json` path and Grok CLI import. A downstream service may want to store credentials in its own database or secret store. A generic storage seam or an explicit-token API should enable that; Eggpass’s restrictive, atomic file store and `~/.grok/auth.json` import can remain optional adapters (`src/auth/store.rs:1-18, 130-195`). Document the concurrency guarantee: the current manager’s mutex coalesces refreshes within a process but is not a cross-process lock (`src/auth/refresh.rs:67-187`). Either make the store contract support cross-process coordination or state that boundary clearly.

**Make Eggfetch ergonomic without hiding its ownership.** Accept a caller-supplied, cloneable `eggfetch_core::Client` so downstream code can reuse its connection pool and configuration. Offer a builder/default convenience only if it does not create a runtime or hide timeout policy. Keep Eggfetch response internals out of public return types; translate them to the library’s own status, OAuth, parsing, timeout, and network errors. The library’s async methods should simply be awaited in the caller’s runtime. Eggfetch’s [0.3.0 Client API](https://docs.rs/eggfetch-core/0.3.0/eggfetch_core/client/struct.Client.html) is async-first; its [Timeout API](https://docs.rs/eggfetch-core/0.3.0/eggfetch_core/timeout/struct.Timeout.html) supports separate pool/connect/write/read/total budgets.

**Keep public types semver-manageable.** Use builders for provider/client configuration, avoid exposing internal module paths, mark extensible error enums non-exhaustive, document ownership and `Send`/`Sync` guarantees, and include compiling Tokio/Eggfetch examples. If the public constructor accepts the Eggfetch `Client` type, the library is coupled to that Eggfetch version line; downstream consumers must align to a compatible line to pass their client directly. Avoid a generic async transport trait in the first version unless transport substitution is a real requirement—it adds API and implementation complexity without helping the stated Eggfetch-first consumers.

## Security and protocol acceptance criteria

The library must retain the safeguards already present in the current auth code and make them part of its public contract:

- Authorization-code flows use PKCE S256, high-entropy state, and nonce; callback state and the exact redirect path are validated. For native apps, [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html) requires PKCE for public clients and recommends an external user-agent. Loopback listeners must bind only to loopback, use a short-lived random port, and close after completion. Do not introduce embedded-login pages.
- Device verification URIs are checked against the provider’s trusted-host policy before the library opens or presents them. Device-code values are not shown to users or placed in logs.
- Async cancellation, request deadlines, and response-size bounds are explicit. Preserve current OAuth timeouts intentionally rather than inheriting Eggfetch defaults accidentally. Do not blindly retry token exchanges or refreshes; document the retry policy, especially around refresh-token rotation.
- The manager preserves the current proactive refresh skew, 401 compare-and-refresh behavior, one-refresh-under-concurrency guarantee, atomic persistence, and rule that a missing rotated refresh token does not erase the existing one (`src/auth/refresh.rs:119-179, 190-225`).
- Public errors may expose status and OAuth error codes, but should not automatically include arbitrary response bodies. Token-bearing values need redacted `Debug` implementations and should never be logged by the library.

Two concrete porting issues need resolution before declaring parity. First, `TokenSet`, `DeviceCode`, and `StoredAuth` currently derive `Debug` while containing access/refresh tokens or device codes (`src/auth/client.rs:51-67, 130-145`; `src/auth/store.rs:44-87`). A public crate should redact those fields (or use secret wrappers) before downstream users can accidentally log them. Second, the current device-flow loop increments the polling interval by **one** second after `slow_down` (`src/auth/flow.rs:277-279`), but [RFC 8628 §3.5](https://www.rfc-editor.org/rfc/rfc8628.html#section-3.5) requires increasing it by five seconds for that and subsequent polls. The loop also clamps `expires_in` to at least 60 seconds (`src/auth/flow.rs:259-264`); review that against the server-provided expiry rather than copying it unquestioned. Async cancellation and timeout retries should also follow RFC 8628’s polling guidance.

## Package, dependency, tests, and release work

A separate `eggpass-auth` workspace package is the cleaner boundary than adding a library target to the existing binary package. The current `Cargo.toml` has a broad CLI/server dependency list and an explicit root-package include list (`Cargo.toml:1-28, 30-77`). A dedicated package can keep its dependency surface focused on Eggfetch, serde/JSON, time/PKCE utilities, and optional storage/loopback adapters. Keep the existing MSRV at Rust 1.89 if using Eggfetch 0.3.0, which also declares Rust 1.89.

The current `.github/workflows/publish-crates.yml` checks and publishes only the root `eggpass` package (`.github/workflows/publish-crates.yml:41-61`). A public auth crate therefore needs its own package verification and publish path, or a deliberate workspace-aware release workflow. Decide whether the auth crate is versioned independently or must ship in lockstep with the CLI; test the exact crate with `cargo package --locked` before publication. Do not assume the existing Eggpack release job or crates.io workflow will automatically publish a second package.

Minimum acceptance tests should cover request form encoding and provider-specific parameters; success, OAuth error, non-JSON error, timeout, and oversized-body handling; PKCE/state/nonce and callback validation; device `authorization_pending`, `slow_down`, denial, expiry, and cancellation; OpenAI issued-client-ID reuse; refresh-token rotation; concurrent access-token refresh; and atomic credential persistence. Run tests against a local stub endpoint using the real Eggfetch client, then compile a small downstream-style consumer that supplies its Eggfetch client and awaits login/refresh without Eggpass CLI or server modules. Keep network-dependent live provider checks separate from deterministic CI.

## Decisions to settle before implementation

1. **MVP flow scope:** async OAuth/token operations only, or also complete browser loopback and device-login orchestration? Recommended: core transaction/polling APIs in the first release; UI and loopback conveniences as optional adapters.
2. **Storage contract:** caller-owned token storage only, or include a default file store? Recommended: caller-owned storage in core; optional Eggpass-compatible file adapter.
3. **Crate/release boundary:** separate `eggpass-auth` package with independent versioning, or couple its release to `eggpass`? Recommended: separate package and explicit publication workflow.
4. **Eggfetch alignment:** accept the current dual 0.2/0.3 dependency graph temporarily, or first update/release the Eggup adapter against Eggfetch 0.3.0? This affects dependency duplication, not the downstream API design.
5. **Provider extensibility:** only the built-in x.ai/OpenAI profiles, or a documented generic OAuth provider configuration as well? Recommended: support the two built-ins and a minimal custom OAuth profile, but keep provider-specific registration semantics explicit.
